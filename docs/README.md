## Why these documents exist

This is a hackathon proof of concept, so documentation must help us **make decisions and ship**, not create bureaucracy.

The set above covers the minimum questions we repeatedly need to answer:

1. **What exactly are we building?** → MVP + PRD
2. **How does it fit together?** → Architecture
3. **How should the AI behave?** → AI System
4. **What do we build next?** → Implementation Plan
5. **What should it look and feel like?** → Design
6. **What can go wrong or be abused?** → Security
7. **How do we know it works?** → Testing
8. **How do we prove it to judges quickly?** → Demo Plan

## Documentation rules

- Keep documents short enough to remain useful.
- Update the relevant document when a real decision changes.
- Label unresolved choices as **Open**, not as facts.
- Do not duplicate entire sections from `context.md`; link or summarize instead.
- Do not silently convert future ideas into MVP requirements.
- Use exact dates for hackathon milestones.
- Keep provider-specific AI/voice choices behind interfaces until a zero-cost provider is intentionally selected.
- Security requirements are build requirements, not post-demo polish.

## Research basis

The documentation set is informed by:
- the Build With AI: Basics requirement for `scope.md`, `prd.md`, and `spec.md`;
- Devpost's guidance to plan backward from the deadline, build/deploy/test, prepare the demo early, and keep the repository understandable;
- Supabase guidance to pair Auth with Row Level Security and keep service-role/secret keys off the client;
- OWASP guidance that prompt injection requires defense in depth rather than a single filtering prompt;
- NIST secure-development guidance to integrate security practices into the development lifecycle rather than treating them as a final phase.
